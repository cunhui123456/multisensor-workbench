# B210 收发中断检查与恢复（2026-11-02）

执行与目标设备：同一 MacBook Pro M5 Max / 64GB，按需运行的多传感器实验台，既有 `rf-gnuradio` / UHD 4.10.0.0。用户确认自有 B210、TX1/RX1 经 SSPP、接线固定，并授权 5.0–5.3 GHz、250 kS/s、TX 20 dB / RX 30 dB、数字幅度 0.3 下最多20秒短测。未更换驱动、FPGA、设备 profile 或测量质量阈值。

## 故障定位与旧版比较

- 用户所给 `sspp-usrp-PySide6-PyQtGraph` 自10月28日起是指向 `multisensor-workbench` 的兼容符号链接，不是两套独立现用代码。
- 与2026-10-10提交 `06163b8` 比较，`hardware.py` 字节相同，扫频 `tx_loop` / `rx_loop` AST相同。近期改变集中在质量窗口、缺测处理、温压联测、总时限与界面；并非没有版本差异，但未发现收发循环被最近预算修改破坏的证据。
- 11:16开始的 `20261102T031625_354476Z` 已完成40点×3轮。12:10、12:11、12:29、12:31四次失败均 `TX send returned zero samples`，随后RX停止 `wait_for_ack / accum_timeout` 超时，无完整停止证据。FPGA、采样率和增益与先前成功记录相同。
- 将当前采集模块仅逆向三处总预算补丁，SHA-256与11:16成功120点记录中的采集模块完全匹配；同期其余记录的源码哈希一致，未发现预算修改改变TX/RX/切频或并行逻辑。
- 12:37独立CLI `20261102T043714_516997Z`（不运行GUI或温压串口）复现相同故障，因此GUI/温压联测并非必要触发条件。
- 系统USB树显示B210位于GenesysLogic扩展坞，链路同时有网卡、Arduino及适配器；只能视为排查线索，不能据此认定扩展坞损坏或带宽不足。

## 同代码断电前后对照

用户确认断电并重连原扩展坞后：

1. `20261102T043824_925365Z` 首次仅加载固件，重新枚举时返回No devices，`rf_start_attempted=false`，没有开始收发。
2. `20261102T043839_144647Z` 在**未修改任何采集代码**的情况下恢复：发送2,600,000样本（10.4秒样本时长）、接收2,539,520样本（10.15808秒）、RX超时0、部分发送0，errors为空，TX EOB / RX stop / workers退出记录齐全。
3. 两频点状态为 `complete_with_gaps`：5.0 GHz / 2 kHz因8秒内频率质量未通过留空（最后窗口峰频1701.5 Hz，偏差298.5 Hz超过200 Hz门限，目标SNR约10.99 dB）；5.3 GHz / 3 kHz通过，约−97.16 dBFS估计。通信恢复不等于全频段测量质量合格、S21标定或长期稳定性验收。

结论：本次已证实的故障层级是B210/UHD数据与控制通信失响应，断电重连使同一新版恢复。更支持设备/USB链路运行状态异常，尚不能区分线缆、供电、扩展坞、设备固件或驱动的具体诱因，也不能以一次短测排除所有时序回归。没有证据支持通过回退软件、加大点时限或降低质量门槛修复此通信故障。

## 软件修正范围

- 扫频TX部分发送立即累计，避免后续失败丢失已提交样本计数。
- 发送1样本EOB必须确认返回1；返回0时记录停止未确认，不再写成功。
- 用结构化 `STOP_STATUS` 区分“正在保存”和“停止证据齐全”；无RF启动时明确未启动；证据不足不再打印“RX/TX stopped”。
- 组合TX停滞和控制ACK超时提供中文USB/供电检查提示，不自动重启发射、不吞掉硬故障，不改写历史manifest。

这属于诊断与停止证据修正，不将它冒称为断电恢复的原因。收发恢复的真机对照发生在代码安装前；安装后只做离线故障注入回归。

## 后续使用

停止并保存当前工作后重新打开日常 `run_desktop.command`，重新初始化USRP。若复发，先保存错误日志，断开USB及外接供电（若有）再接；优先另用独立USB接口和已知良好线缆做对照。初始化成功仅证明打开设备，不等于持续收发正常。无需恢复旧目录或旧质量算法。
